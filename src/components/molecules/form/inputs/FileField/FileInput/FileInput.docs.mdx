# FileInput

> Styled file upload input with drag-and-drop via react-dropzone. Supports multi-file upload with async per-file processing, duplicate/size/count validation with toast feedback, and loading states per file. For form integration with validation and labels, use FileField.

<br/>

## Features

- Async per-file upload with progress callback
- Validation — duplicate, size, and count
- Error recovery via toast feedback

<br/>

## Component Definition

### Semantics & HTML
- Outer `<div>` wraps everything (`flex flex-col gap-2`) — contains the dropzone and the file list
- Dropzone wrapper `<div>` — receives `getRootProps()` from react-dropzone, carries variant/color/size/error/disabled styling, `data-testid="InputWrap"`
- `role="presentation"` on the dropzone wrapper — set by react-dropzone's `getRootProps()`. The wrapper is a click-through surface to the hidden input, not a standalone interactive element
- Hidden `<input type="file">` inside the dropzone — receives `getInputProps()` from react-dropzone, `id` and `name` from the `name` prop. `accept` attribute is auto-generated by react-dropzone from the `allowedFileTypes` prop
- `className` lands on the dropzone wrapper div, not the outer container
- `ref` forwards to the dropzone wrapper `HTMLDivElement`, not the hidden input — the wrapper is what consumers interact with programmatically (focus, scroll into view)
- File list renders `FileDetail` components below the dropzone, each displaying file name, size, and a delete button

### Keyboard Handling
- **Enter / Space** — Opens the native file picker dialog via react-dropzone's `open()` function
- **Disabled** — Blocks Enter/Space with early return in `handleKeyDown`
- **Loading** — Blocks Enter/Space while any file is uploading (`isUploading` guard)
- No keyboard handling for file list navigation — delete buttons are standard `Button` components with their own keyboard behavior

### Accessibility (WAI-ARIA)
- No specific WAI-ARIA file upload pattern exists — follows the common dropzone pattern used across major libraries
- Hidden `<input type="file">` is the actual form control; dropzone wrapper is the visual/interaction surface
- `aria-disabled="true"` on wrapper when disabled
- No `aria-label` or `aria-labelledby` on the hidden input by default — labeling comes from Field level via `<label htmlFor>`. Standalone consumers can pass `aria-label` through rest props
- FileDetail delete buttons have `aria-label` with file name via i18n: `t('Components.delete', { label: file.name })`
- FileDetail uses `aria-busy="true"` on the delete button during loading, `role="status"` on InlineLoader

### Visual States
- **Default** — Dashed border, variant/color combination from the style system (text, outlined, contained × primary, secondary, terciary)
- **Drag active** — Message text changes to drop prompt via `isDragActive` from useDropzone
- **Focus-within** — Ring on wrapper via `focus-within:ring-1` + `focusWithinVariant`
- **Error** — `.error` class on wrapper, red border/shadow via `errorStateClass`
- **Disabled** — `.disabled` class + `disabledVariant` on wrapper, `aria-disabled`, cursor changes
- **File loading** — Individual FileDetail replaces text with a loader: Ghost skeleton (no progress) or ProgressBar (with progress). Delete button shows `aria-busy="true"`

### Interaction Behavior
- **Drop/click** — react-dropzone handles drag events and click-to-browse. `handleDrop` validates file count first (rejects entire batch if over `maxFileCount`), then filters individual files for size and duplicate checks
- **Async upload** — Each valid file is added to `fileList` with `isLoading: true`, then `onDrop(file, onProgress)` is called per file. The consumer can optionally call `onProgress(percent)` (0-100) during upload — when called, FileDetail renders a `ProgressBar` replacing text entirely. When not called, Ghost skeleton replaces text instead. On success, the file state updates to `isLoading: false` and text reappears. On failure, the file is removed from the list and an error toast is shown
- **Delete** — Sets the target file to loading state, calls `onDelete`, then removes it from the list
- **Validation toasts** — via `useToast().addToast('error', ...)` for: max file count exceeded, max file size exceeded, duplicate file (matched by `name-size-lastModified` composite ID)
- `onDropAccepted` and `onDropRejected` are passed through to `useDropzone` for consumers who need react-dropzone's own validation hooks

### Responsive & Layout
- Dropzone wrapper is `w-full` block-level, fills container width
- File list stacks vertically below the dropzone with `gap-2`
- FileDetail uses `max-w-full` with Ellipsis for long file names

## Architecture Decisions
- **`react-dropzone` integration**: Handles cross-browser drag-and-drop complexity (drag enter/leave counting, file type filtering, drop event normalization). The component only owns validation logic and state management on top.
- **Per-file async upload with optional progress**: `onDrop(file, onProgress)` returns `Promise<T>` per file. The `onProgress` callback is always provided — consumers opt in by calling it. When called, FileDetail switches from InlineLoader to ProgressBar automatically. This avoids a boolean prop and keeps the API self-documenting: if you don't need progress, ignore the second argument. Progress requires `XMLHttpRequest` with `upload.onprogress` on the consumer side — standard `fetch` doesn't support upload progress.
- **Internal `fileList` state with value sync**: Manages `{file, isLoading}` pairs internally rather than requiring the consumer to track loading states. The `value` prop seeds the initial list and syncs via `useEffect` when it changes — enabling parent-driven updates (e.g., FileField's react-hook-form integration) while keeping the loading lifecycle internal.
- **`accept` via `useDropzone`**: `useDropzone` receives an `accept` object for both drag-and-drop and click-to-browse type filtering. react-dropzone auto-generates the native `accept` attribute on the hidden input. Both are derived from the `allowedFileTypes` prop.
- **`generateFileId` composite key**: Exported for use by FileField. Used consistently across all identity operations — deduplication, error recovery, delete, and React keys. The `name-size-lastModified` composite prevents collisions between files with the same name from different directories.
- **Ref to wrapper div, not input**: The hidden input is visually absent and managed by react-dropzone. The wrapper div is what consumers interact with programmatically (focus, scroll into view). This differs from TextInput's pattern but matches the component's structure — there's no visible input to ref.

## Known Bugs & Limitations
- **Batch rejection drops all files** (medium) — When a drop exceeds `maxFileCount`, the entire batch is rejected even if some files could fit. A user dragging 3 files when 2 slots remain gets zero uploaded with only a toast.
- **File size always displays in MB** (low) — `toFixed(2)` in FileDetail always shows MB, so a 500-byte file reads "0.00 MB".

## Review

> FileInput is a well-structured upload component that earns its complexity — async per-file uploads with progress tracking, deduplication, and error recovery are all handled internally so consumers just provide an `onDrop` that returns a promise. The `onProgress` callback design is particularly clean: always available, zero cost to ignore, and FileDetail automatically switches between InlineLoader and ProgressBar based on whether it was called. That's a smart API surface.
>
> Compared to MUI's file upload story (which is basically "use a Button with `component='label'` and build everything yourself"), this is a complete solution. MUI forces consumers to manage file lists, validation, progress states, and error handling from scratch. FileInput bakes all of that in with sensible defaults — 5 files, 5MB limit, PDF/JPEG/PNG — while staying flexible through props. The tradeoff is that MUI gives you total control, but for the 90% case, FileInput's opinionated approach is the better call.
>
> The `handleDrop` early return on exceeding `maxFileCount` silently drops all files in the batch, even if some could fit — a user dragging 3 files when 2 slots remain gets zero uploaded with only a toast. That's a realistic frustration point. The file size display in FileDetail always shows MB (`.toFixed(2)`) even for tiny files, so a 500-byte file reads "0.00 MB," which is unhelpful. Everything else is solid: the ref-to-wrapper decision makes sense, `generateFileId` is a clean composite key, and the `useEffect` sync with `value` keeps parent-driven updates working without leaking loading state.
>
> A practical, well-defaulted upload component with one batch-rejection edge case worth smoothing out.
>
