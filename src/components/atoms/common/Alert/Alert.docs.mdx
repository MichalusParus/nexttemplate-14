# Alert

> Static feedback container for success, info, warning, and error messages. Used for form validation summaries, system notifications, and contextual status feedback within page content.

<br/>

## Features

- Status variants — success, info, warning, error, none
- Optional title heading
- Start and end icon slots

<br/>

## Component Definition

### Semantics & HTML
- Native `<div>` element — no implicit ARIA role on the generic container
- `role="alert"` applied only for `status="error"` — maps to WAI-ARIA alert (assertive live region), screen readers will interrupt and announce the full content
- Non-error statuses (`success`, `info`, `warning`) have no role — treated as static inline content
- Status icons (`SuccessIcon`, `InfoIcon`, `WarningIcon`, `ErrorIcon`) rendered with `aria-hidden="true"` — purely decorative, status is conveyed through color and context
- Custom `startIcon` allowed only when `status="none"` — prevents conflict with built-in status icons
- `endIcon` rendered unconditionally with no `aria-hidden` — left to the consumer because it could be decorative or actionable (e.g., close button)
- Title rendered via `<Span variant="bold">` inside an inner wrapper div

### Accessibility (WAI-ARIA)
- Follows [WAI-ARIA Alert Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alert/) for error status only
- `role="alert"` implies `aria-live="assertive"` and `aria-atomic="true"` — screen readers interrupt current speech to announce the alert content
- Non-error statuses intentionally have no live region semantics — they are static content that does not require announcement
- Status icons are `aria-hidden="true"` so screen readers do not announce redundant icon labels

### Responsive & Layout
- `flex items-start` — icon and content side-by-side, icon top-aligned
- Inner content wraps in a flex column for title + children stacking
- `rounded-md border` base styling
- Width fills parent container; constrain via `className` (e.g., `max-w-96`)

<br/>

## Architecture Decisions
- **`role="alert"` only on error**: WAI-ARIA `role="alert"` is assertive and interrupts screen reader flow. For success/info/warning messages that appear as inline static feedback (not dynamically injected), no role avoids unnecessary interruptions. If the component were used for live toast-style notifications, `role="status"` (polite) would be appropriate for non-error statuses — but that's a different usage pattern.
- **`startIcon` gated behind `status="none"`**: Prevents consumers from accidentally overriding the built-in status icon, which would create a visual/semantic mismatch between the status color and the displayed icon.
- **`endIcon` has no `aria-hidden`**: Left to the consumer because the icon could be decorative (should have `aria-hidden="true"`) or actionable (close button, should have accessible label). Adding `aria-hidden` by default would break actionable use cases.
- **No `role="status"` for non-error statuses**: `role="status"` implies `aria-live="polite"`, which only announces *changes* to content. If the alert renders on mount (the common case), nothing gets announced. If dynamically injected, every re-render or content change triggers a polite announcement, which is noisy. For this component's static inline usage, neither behavior is useful.
- **Live-region responsibility belongs to the consuming context**: Alert is a static display component — it doesn't know whether it was in the DOM on page load or dynamically injected. When alerts are used as toast notifications, the consuming component (ToastProvider) wraps them in a live region (`role="status"` or `aria-live="polite"`). This keeps Alert focused on presentation and avoids double-announcing when both Alert and its wrapper have live-region roles.
- **No built-in `onClose`**: The `endIcon` slot already accepts any ReactNode — a Button with custom icon, handler, and styling, or a plain decorative icon. A hardcoded `onClose` prop would be less flexible (locked to one button pattern) for minimal code savings. Composition over configuration.
- **`items-start` alignment**: Optimized for the common multi-line case (title + description) where the status icon should align to the top of the content block. Single-line alerts with endIcon may need `items-center` via className — changing the default to `items-center` would break multi-line layout where the icon would float to the vertical center of the whole block.

## Known Bugs & Limitations
- **[Low]** `items-start` alignment means endIcon sits at the top on single-line alerts — override with `items-center` via className when endIcon needs vertical centering.

## Review

> The `status="none"` escape hatch is the detail that sold me — it turns a rigid status alert into a general-purpose callout without bloating the API. Most alert components force you to pick a semantic status even when you just want a highlighted block with a custom icon, and gating `startIcon` behind `none` keeps the happy path clean while still offering full control.
>
> Chakra UI's Alert takes a different approach: status drives the icon automatically (like here), but there's no opt-out — you either use their five statuses or you're fighting the component. This design is strictly more flexible. Chakra also ships a dedicated `CloseButton` composite, but the `endIcon` slot here achieves the same thing with less API surface, and leaving `aria-hidden` to the consumer is the right call since a close button needs to be focusable, not hidden.
>
> Solid alert with a smart API — the `none` status and composition-first `endIcon` slot outperform most libraries I've used.
>
