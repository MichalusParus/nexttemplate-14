# Chip

> Small styled container for displaying compact information — selected options, tags, user badges, and metadata labels. A non-interactive Button visually: same pill shape, same `contained` default, same icon slots.

<br/>

## Features

- Optional title heading
- Start and end icon slots

<br/>

## Component Definition

### Semantics & HTML
- Native `<div>` element — no implicit ARIA role, purely presentational container
- Children rendered inside `<Span variant="none">` with `overflow-hidden text-ellipsis whitespace-nowrap` — single-line with truncation when width is constrained
- Optional `title` rendered via `<Span variant="bold">` (renders as `<strong>`) above children in a flex column
- `startIcon` and `endIcon` slots accept any ReactNode — commonly used for Avatar, ProfileIcon, or a close Button

### Accessibility (WAI-ARIA)
- No ARIA role — presentational container, not interactive
- Icons passed via `startIcon`/`endIcon` should include their own accessibility attributes — the chip does not manage them
- No `aria-label` on the chip itself — content is exposed through its text children

### Responsive & Layout
- `flex items-center gap-1` — horizontal layout with icon and content side-by-side
- `max-w-max` — chip sizes to content by default. Consumer overrides with `max-w-*` via className to constrain width and activate truncation
- `rounded-3xl` pill shape, `px-2` base padding. Stories demonstrate `pl-0`/`pr-0` overrides when icons touch the edge
- Inner content in flex column for title + children stacking
- `text-inherit` on children Span — color comes from the chip's variant/color system

<br/>

## Architecture Decisions
- **Follows Button's visual defaults**: `contained` + `primary`, same as Button. Same pill shape, same visual weight, same icon slots. The contained default gives chips visual prominence inside larger containers (selects, form fields)
- **Interactivity via composition, not props**: No `onClick`, `onDelete`, `tabIndex`, or keyboard handling on the chip itself. Interactive behavior is composed by passing elements (Button, Avatar) into `startIcon`/`endIcon` slots — fully consumer-controlled. Clickable chip = use Button directly
- **Truncation-ready children**: `overflow-hidden text-ellipsis whitespace-nowrap` on children Span. Harmless at default width (`max-w-max`), activates when consumer constrains width via className. No tooltip — consumer wraps children in `<Ellipsis>` for tooltip-on-truncation

<br/>

## Known Bugs & Limitations
- **[Low]** Truncation is CSS-only — no tooltip showing full text on hover. Consumer wraps children in `<Ellipsis>` component for tooltip-on-truncation, but this adds molecule-level complexity

## Review

> A chip that knows what it isn't — that's the design move here. No onClick, no onDelete, no keyboard handling. Just a styled container with icon slots and built-in truncation. Need interaction? Reach for Button. That's a genuinely clear boundary that most libraries get wrong by stuffing both roles into one component.
>
> MUI's Chip is the obvious comparison, and it's a kitchen sink: clickable, deletable, avatar slot, ripple effects, and a pile of internal state management for keyboard interactions. That's fine for a distributed library where you can't touch the source — but in a copy-paste codebase, all that conditional logic is dead weight when half your chips are just status badges. This version deletes the problem instead of solving it, and that's the right call. The title + children split gives you a two-line chip for free, which MUI needs custom content for, and the built-in truncation on children keeps everything single-line by default — exactly what a tag-sized element should do.
>
> A display chip that earns its simplicity by genuinely not needing what it leaves out.
>
> — *Claude, Opus 4.6, 2026-03-20*
