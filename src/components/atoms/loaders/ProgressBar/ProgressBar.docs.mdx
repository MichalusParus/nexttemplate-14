# ProgressBar

> Linear progress bar with determinate and indeterminate modes. Pass a `progress` value (0–100) for determinate; omit it for an animated indeterminate bar. Customizable `color` and `height`. Uses `next-intl` for the accessible `aria-label`.

<br/>

## Component Definition

### Semantics & HTML
- Native `<div>` wrapper with `role="progressbar"` and `aria-label` via `next-intl`
- **Determinate** (`progress` is a number): `aria-valuemin=0`, `aria-valuemax=100`, `aria-valuenow` (clamped). Inner bar width set via inline `style` percentage with 200ms transition
- **Indeterminate** (`progress` is `undefined`, the default): `aria-valuemin`, `aria-valuemax`, `aria-valuenow` are omitted per WAI-ARIA spec. Inner bar has fixed `w-1/3` width with `animate-progress-bar` sliding animation
- Inner `<div>` (`.Progress`) represents the filled portion
- Accepts all native `HTMLDivElement` attributes via rest props spread
- Queryable by `role="progressbar"`

### Accessibility (WAI-ARIA)
- `role="progressbar"` is correct for both modes — per WAI-ARIA, omitting `aria-valuenow` signals indeterminate state to screen readers
- Determinate: `aria-valuenow` updates with the clamped progress value — screen readers announce percentage changes. `aria-valuetext` can be passed via rest props for human-readable descriptions (e.g., `aria-valuetext="Step 3 of 5"`)
- Indeterminate: no value attributes — screen readers announce "loading, progress bar" without a percentage
- `aria-label` is translated via `next-intl` (`useTranslations('Components')`)
- Indeterminate animation respects `prefers-reduced-motion: reduce` — sliding bar stops for users with reduced motion enabled (global CSS rule)
- [WAI-ARIA progressbar role](https://www.w3.org/WAI/ARIA/apd/#progressbar)

### Responsive & Layout
- `w-full` — fills parent width, height controlled via `height` prop (default `h-3`)
- Container: `overflow-hidden rounded-md border` with background color from theme
- Inner bar: `rounded-xs`, color via `[&>.Progress]` child selector
- Determinate: width as percentage via inline style, `200ms width linear` transition
- Indeterminate: `w-1/3` fixed width, `animate-progress-bar` keyframes (`translateX(-100%)` → `translateX(300%)`, 1500ms ease-in-out infinite)

<br/>

## Architecture Decisions
- **Indeterminate as default**: `progress` defaults to `undefined` — a ProgressBar with no props renders as indeterminate. Pass `progress={0}` for an explicit empty determinate bar. Matches MUI's default behavior.
- **Same DOM structure for both modes**: No conditional rendering or alternate paths. The only differences are ARIA attributes and whether the inner bar uses inline width style or animation class.
- **Clamping**: `Math.min(100, Math.max(0, progress))` ensures the bar never overflows or goes negative. Both `aria-valuenow` and width use the clamped value.
- **`height` as Tailwind class string**: Unlike CircularLoader/InlineLoader/Ghost — which are self-contained shapes where preset sizes make sense — a progress bar is a layout-filling element where height depends on context (thin `h-1` accent bar, standard `h-3`, chunky `h-6` with a label). A Tailwind class string gives full control without artificial constraints. Default `h-3`.
- **Color via child selector**: `progressColor` uses `[&>.Progress]:bg-{color}-800` to style the inner bar from the container. Same pattern as CircularLoader's `[&>.Spinner]`.
- **`role="progressbar"` for both modes**: Unlike CircularLoader (which uses `role="status"` for indeterminate), ProgressBar uses `role="progressbar"` in both modes. WAI-ARIA spec allows this — the presence or absence of `aria-valuenow` distinguishes determinate from indeterminate.
- **`aria-valuetext` via rest props**: No dedicated prop needed — `aria-valuetext` is a native attribute supported through rest props spread. Consumers pass it directly (e.g., `aria-valuetext="Step 3 of 5"`). Simpler than Radix's `getValueLabel` callback — no abstraction over a one-liner.

## Review

> Clean little progress bar. The indeterminate-by-default design is a smart call — you drop `<ProgressBar />` in a loading state and it just works, then pass `progress={50}` when you have a real value, same DOM either way. Clamping silently is the right move too; no one wants a 103% wide bar crashing their layout. The conditional ARIA attributes — only setting `aria-valuemin`, `aria-valuemax`, and `aria-valuenow` in determinate mode — is the correct spec behavior that most libraries get wrong by always emitting all three.
>
> Tight component. Does exactly what it should and composes without friction.
