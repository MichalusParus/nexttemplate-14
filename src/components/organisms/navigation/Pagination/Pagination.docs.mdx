# Pagination

> Three independently usable pagination components: `Pagination` (responsive wrapper — auto-switches between mobile and screen variants by viewport width), `MobilePagination` (compact "3 / 5" display), and `ScreenPagination` (full page buttons with ellipsis and fixed page spread). Use the responsive wrapper for automatic layout, or the sub-components directly for fixed layouts. Pairs with `usePagination` for client-side data slicing with built-in load-more support.

<br/>

## Features

- Three exported components — use `Pagination` for automatic responsive switching, or `MobilePagination` / `ScreenPagination` independently for fixed layouts
- Responsive layout (`Pagination`) — auto-switches between MobilePagination and ScreenPagination based on viewport width
- Six breakpoint-driven page spreads (7, 9, 11, 13, 15, 17) with configurable `maxSpread` cap
- Load More button (ScreenPagination only) with `loadMoreCount` tracking — selected range highlights across multiple pages. MobilePagination displays the range in text ("3-5 / 10") but has no Load More button
- Ellipsis collapse — first/last page buttons with dot separators appear when page count exceeds the spread threshold
- `hideNav` prop swaps `<nav>` for `<div>` when pagination isn't the primary navigation landmark
- `usePagination` hook for client-side array pagination with automatic page reset on search param changes

<br/>

## Component Definition

### Semantics & HTML
- **Pagination (responsive wrapper)**: `<div>` with `forwardRef` — delegates to MobilePagination or ScreenPagination based on `useResponsivePageSpread` result (0 = mobile, 7–17 = screen)
- **MobilePagination**: Root element is `<nav>` (or `<div>` when `hideNav`) with `aria-label="Pagination"`. Contains two chevron Buttons (previous/next, conditionally rendered at boundaries) and a `<P>` text element showing "page / count" or "page-range / count" format
- **ScreenPagination**: Outer `<div>` wrapper (receives `ref` and `className`), inner `<nav>` (or `<div>` when `hideNav`) with `aria-label="Pagination"`. Contains: optional Load More Button above pagination, left/right chevron Buttons (conditionally rendered at boundaries), page number Buttons, and ellipsis dot divs (`role="presentation"`, `aria-hidden="true"`)
- Page buttons use `startIcon={String(pageNum)}` — rendered as icon-only buttons with number text
- Selected pages get `className="selected"`, current page gets `aria-current="page"`
- Chevron buttons have `tabIndex={-1}` (ScreenPagination only) — excluded from keyboard navigation, page-button arrow keys provide navigation. MobilePagination chevrons are standard focusable Buttons in the normal Tab order
- Single page or `count=0` renders pagination with `invisible` class

### Keyboard Handling
- **ArrowDown / ArrowUp / ArrowLeft / ArrowRight** — Navigate between page buttons via `useFocus` roving tabindex (ScreenPagination only)
- **Enter / Space** — Activate focused page button (inherited from Button)
- **Home / End** — Jump to first/last focusable page button
- Chevron buttons have `tabIndex={-1}` (ScreenPagination only) — not in the keyboard tab sequence, navigation is page-button-only
- MobilePagination has no custom keyboard handling — chevrons are standard focusable Buttons, Tab navigates between them
- Loading state disables all buttons (`aria-disabled`)

### Accessibility (WAI-ARIA)
- `<nav aria-label="Pagination">` provides navigation landmark (unless `hideNav`)
- Each page button: `aria-label="page N"`, `aria-current="page"` on the active page
- Chevron buttons: `aria-label="previous page N"` / `aria-label="next page N"` with computed target page
- Ellipsis dots: `role="presentation"`, `aria-hidden="true"` — hidden from assistive technology
- Loading state: all buttons receive `aria-disabled="true"` via Button's disabled handling
- No specific WAI-ARIA pagination pattern exists — follows [Navigation landmark](https://www.w3.org/WAI/ARIA/apg/patterns/landmarks/) with `aria-current` for page indication

### Visual States
- **Selected**: `selected` class on current page and load-more range pages
- **Disabled/Loading**: All buttons disabled via `aria-disabled`. ScreenPagination keeps both chevrons visible (disabled) during loading regardless of page position (`page !== 1 || isLoading`, `page + loadMoreCount < count || isLoading`). MobilePagination hides chevrons at boundaries even during loading
- **Invisible**: `count <= 1` hides pagination with `invisible` class (reserves layout space)
- **Boundary states (MobilePagination)**: Left chevron hidden when `page === 1`, right chevron hidden when `page + loadMoreCount >= count`
- **Boundary states (ScreenPagination)**: Same as mobile, except during loading — both chevrons render as disabled skeleton affordances at all page positions
- **Load More visible**: Only when `onLoadMore` provided AND `page + loadMoreCount < count` (ScreenPagination only)

### Interaction Behavior
- **Page click**: Fires `onChange(pageNum)` — consumer manages page state
- **Previous chevron**: Fires `onChange(page - 1)`. In MobilePagination, if navigating to page 1, focus transfers to next button
- **Next chevron**: Fires `onChange(page + loadMoreCount + 1)`. In MobilePagination, if navigating to last page, focus transfers to previous button
- **Load More**: Fires `onLoadMore()` — consumer increments `loadMoreCount`, pagination highlights the expanded page range
- **Loading state**: All navigation disabled. ScreenPagination chevrons remain visible but inactive (even at boundaries), and shows skeleton page buttons (min 5, capped at pageSpread). MobilePagination hides chevrons at boundaries during loading

### Responsive & Layout
- ScreenPagination outer wrapper: `flex flex-col items-center` — Load More button stacks above page buttons
- ScreenPagination nav: `relative flex w-max` — inline, width determined by page spread
- MobilePagination: `relative w-max` — inline, compact
- Chevron buttons: absolutely positioned outside the pagination body via negative margin/position classes per size
- Page button minimum widths scale with size (`min-w-8` sm, `min-w-9.5` md, `min-w-11` lg)

## Architecture Decisions
- **Responsive split into two components**: Rather than conditionally hiding/showing elements at CSS breakpoints, Pagination renders entirely different component trees (MobilePagination vs ScreenPagination) based on JS-measured viewport width. This avoids rendering 17 page buttons on mobile just to hide them, and lets each variant optimize its own UX — compact "3 / 5" text vs full button grid.
- **`useResponsivePageSpread` returns 0 for mobile**: The page spread enum doubles as the mobile/screen discriminator. `0` means "below smallest breakpoint" → render MobilePagination. Any other value (7–17) is the literal number of visible page button slots for ScreenPagination. No separate "isMobile" boolean needed.
- **Ellipsis algorithm based on `sidePagesCount`**: `(pageSpread - 5) / 2` computes how many pages show on each side of the current page. The `-5` accounts for: current page + first page + last page + 2 ellipsis slots. This makes the spread value directly control layout width without additional configuration.
- **`loadMoreCount` as a range highlighter**: Instead of a separate "selected pages" array, `loadMoreCount` extends the selection from `page` to `page + loadMoreCount`. `isSelected` checks `pageNum >= page && pageNum <= page + loadMoreCount`. The right chevron advances by `page + loadMoreCount + 1` to skip past the loaded range.
- **Chevron buttons use `tabIndex={-1}`**: Arrow navigation between page buttons via `useFocus` is the primary keyboard pattern. Chevrons are mouse/touch affordances — including them in Tab order would create a confusing sequence (Tab to chevron → Tab to page 1 → Tab to page 2...). Arrow keys within the page button group provide the same navigation more efficiently.
- **MobilePagination focus transfer on boundary**: When navigating to page 1 (previous button disappears), focus is proactively moved to the next button before the DOM change. Same for navigating to the last page. Without this, focus would be lost to `<body>` when the clicked button unmounts.
- **`useFocus` with `.PageButton` selector**: The focus system targets elements with the `PageButton` class rather than a role query. This is because all elements are `role="button"` (including chevrons), but only page number buttons should participate in arrow-key navigation.
- **`usePagination` hook is decoupled**: The hook manages client-side array slicing, page state, and load-more accumulation, but returns primitives (`page`, `loadMoreCount`, `onChange`, `onLoadMore`) that map directly to Pagination props. No tight coupling — server-side pagination (like the Pokemon API story) uses the same Pagination component with manual state.
- **`aria-current="page"` on single page, `selected` class on range**: The `selected` CSS class highlights the full loadMore range `[page, page + loadMoreCount]` as a visual affordance showing which pages are currently loaded. `aria-current="page"` is only set on the single active `page` — correct per spec, since only one page is semantically "current". The visual range and semantic current are intentionally different.

## Review

> The responsive split is the best idea here — mobile pagination genuinely needs a different component, not a CSS hack over the same DOM. Measuring viewport width in JS to swap entire component trees is a real commitment, but it pays off: the mobile "3 / 5" display and the full button grid have nothing in common structurally, so pretending they do would just create conditional spaghetti.
>
> MUI's Pagination takes the opposite stance — one component, one DOM tree, CSS handles the rest. That works fine until you need a compact mobile layout, at which point you're hiding buttons with `sx` props and fighting the component instead of using it. The tradeoff here is better: two focused components beat one component trying to be everything. MUI's ellipsis algorithm is battle-tested, but the core advantage of owning the source plus `buttonProps` forwarding on every button means customization isn't a concern — you can modify anything directly.
>
> The `loadMoreCount` range highlighting is clever — a single integer controlling both visual selection and chevron math keeps the API tight. The boundary focus transfer in MobilePagination is a nice touch that most pagination components ignore entirely. The `devWarning` guards for out-of-range `page` and negative `count` catch real misuse at dev time without runtime cost.
>
> A well-shaped pagination that chose the hard structural win over the easy single-component path.
